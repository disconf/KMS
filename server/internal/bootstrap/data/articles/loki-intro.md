## 它是什么

Loki 是 Grafana 家族的**日志聚合系统**：只给日志建「标签索引」（像 Prometheus 的
label），不索引正文，查询时用 LogQL 按标签锁定小范围再暴力扫正文。
设计目标是**便宜**——同样体量日志，存储成本通常只有 ES 的零头。

## 解决什么问题

ES 全文索引的代价是巨量 CPU 与磁盘；而大部分日志查询其实是「先选服务/主机/时间段，
再 grep」。Loki 把「选范围」交给标签索引，「找内容」交给压缩存储上的顺序扫描，
用少量检索性能换来一个量级的成本下降。

## 架构与核心概念

| 概念 | 一句话 |
|---|---|
| 标签（label） | 每条流的 key=value（job、host、app），索引只建在标签上 |
| 日志流（stream） | 同一组标签值的日志序列，标签组合决定流的数量 |
| LogQL | 类 PromQL：`{标签选择} | 管道过滤 | 聚合` |
| 采集端 | Promtail（传统）/ Alloy / Docker driver / OTel |
| 形态 | 单体（SS）模式与微服务模式（读写分离），按规模选 |

**核心心法：标签要克制。** 流的数量 = 标签组合的笛卡尔积，一个高基数标签（如 trace_id）
就能把系统打死——这与 ES「字段随便建索引」是相反的直觉。

## 版本与生态

- 3.x 主线；与 Grafana/Alloy 同节奏发版；
- 采集端在向 **Alloy**（OTel 采集器的 Grafana 发行版）迁移，新项目建议直接评估 Alloy；
- 存储：本地磁盘、S3/OSS 对象存储（生产推荐，天然多副本）。

## 适用与不适用

**适合**：基础设施与应用日志的集中检索、按服务/主机的日志量分析、成本敏感的中小团队。
**不适合**：全文检索需求重的场景（大范围模糊搜索慢）、需要复杂聚合分析商业数据的场景。
