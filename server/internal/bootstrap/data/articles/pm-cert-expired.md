## 一句话结论

入口 HTTPS 证书在凌晨 03:00 到期，自动续签脚本把新证书拷贝到了位却没有 reload nginx，进程仍持有旧证书；早上 08:30 用户集中访问时全站 502，持续 26 分钟。

## 影响范围

- 受影响业务：全部站点（Web、API 均走同一入口）
- 起止时间：08:31 第一起用户反馈，08:57 恢复
- 影响面：约 26 分钟内所有新连接握手失败；已建立的长连接不受影响（这也是为什么有人"打得开"、有人"打不开"，让人误以为是局部网络问题）

## 时间线

| 时间 | 发生了什么 | 谁在处理 |
| --- | --- | --- |
| 03:00 | 证书过期（有效期 90 天） | 无人察觉 |
| 03:02 | 续签定时任务执行成功，新证书写入 `/etc/nginx/ssl/` | 自动化 |
| 08:31 | 客服反馈"网站打不开"，值班尝试访问复现 | 值班 |
| 08:38 | `curl -v https://站点` 报 `certificate has expired` | 值班 |
| 08:45 | 确认磁盘上的证书文件是新证书（未过期） | 值班 |
| 08:52 | `nginx -t` 通过，`nginx -s reload` 执行 | 值班 |
| 08:57 | 外部验证握手正常，业务恢复 | 值班 |

## 排查过程

第一步先区分"证书问题"还是"服务问题"。用 curl 拿到确切的失败原因：

```bash
curl -vI https://www.example.com
# SSL certificate problem: certificate has expired
```

这一步就把 90% 的可能性排除了：不是 DNS、不是防火墙、不是后端 502。

然后对比"磁盘上的证书"和"线上正在用的证书"——这两个东西可以不一致，这正是本次事故的核心：

```bash
# 磁盘上的文件
openssl x509 -in /etc/nginx/ssl/site.pem -noout -dates

# 服务实际吐出来的证书
echo | openssl s_client -connect www.example.com:443 -servername www.example.com 2>/dev/null \
  | openssl x509 -noout -dates
```

两条命令的结果一对比就清楚了：磁盘文件是 90 天后到期的新证书，线上吐出来的是当天 03:00 到期的旧证书。

**结论**：nginx 进程还持有旧证书。文件换了，进程没换。

为什么 `nginx -t` 是通的？因为配置语法没问题——证书文件本身是合法 PEM，只是进程没重新加载。**语法检查不会告诉你"进程里还是旧证书"**。

## 根因

- **直接原因**：证书过期后没有 reload，nginx 继续使用启动时加载的证书。
- **深层原因**：续签脚本的职责被切成了两半——"取证书"是自动化的，"让服务用上"是人工的，而交接处没有任何校验。脚本成功退出（exit 0），看起来一切正常。
- **为什么没早发现**：监控只探"443 端口是否可连"，而端口在证书过期后依然可连（握手才失败）；也没有任何证书到期提醒。

## 修复与恢复

```bash
docker exec nginx nginx -t && docker exec nginx nginx -s reload
```

reload 是平滑的：旧 worker 处理完存量连接后退出，新 worker 用新证书，不掉连接。

验证不能只看"命令执行成功"：

```bash
echo | openssl s_client -connect www.example.com:443 -servername www.example.com 2>/dev/null \
  | openssl x509 -noout -subject -dates
```

必须看到新的到期时间，才算真的生效。

## 改进项

| 改进 | 类型 | 负责人 | 期限 |
| --- | --- | --- | --- |
| 证书到期监控：30 / 14 / 7 / 1 天各报一次，直接读线上证书（`s_client`）而不是读磁盘文件 | 监控 | 运维 | 三天 |
| 续签脚本改成"写入 → nginx -t → reload → 外部 s_client 校验"，任何一步失败告警 | 自动化 | 运维 | 三天 |
| 证书改为 90 天短效 + 自动续签（certbot / ACME），减少人工介入 | 架构 | 运维 | 一个月 |
| 健康检查加一条"证书剩余天数 > 7"的探针，纳入发布前检查 | 监控 | 平台 | 一周 |
| 变更记录里写明"证书类变更必须 reload"，并做成发布单的一个勾选项 | 流程 | 值班 | 一周 |

## 一个容易忽略的细节

这次事故里最贵的不是 26 分钟，而是排查方向。第一反应是"网站打不开"→去查后端服务，而 `curl` 一句话就能定位到 TLS 层。值班手册里应该有这样一条：

> HTTPS 站点"打不开"时，先 `curl -vI`，看失败点落在 DNS、TCP、TLS 还是 HTTP。

四层各自的排查动作完全不同，跳过这一步就是在猜。
